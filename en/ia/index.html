Applied AI in education

Artificial intelligence features in use inside the systems I build — and the way I use AI to build software.

What is already running

The AI here is not a demo: it sits inside two systems used by the people who produce the courses and the people who teach them in vocational education. Every one of these features was designed, implemented and shipped by me.

In FLOW — e-learning content production

  • Contextual assistant in the editor — a chat that knows the lesson currently open. Answers arrive by streaming, token by token, and the lesson content is not re-sent with every question: it is stored as context with a hash, and only a real edit to the lesson opens a new chain.
  • Assisted proofreading — the AI walks the lesson sections and returns proposed corrections, shown as a diff for the proofreader to accept or reject. The proofreader remains the one who decides.
  • Personalized assessment inside the course — a conversational simulator for the student, with the conversation chained by the API itself from one message to the next.

In SENAI Class — the classroom

A tool for teachers to bring gamified activities into the room: game-show style quizzes, learning situations and interactive lessons, with a leaderboard and history.

  • Question generation from a topic — single choice, multiple selection and open questions, as many of each type as the teacher asks for. Questions already generated go into an exclusion list, so the next round does not repeat what already exists.
  • Grading of open answers — the AI compares the student's answer with what was expected, returns a verdict (correct, partial or wrong) and writes the feedback. The teacher reviews and can change it before it counts.
  • Learning situations and interactive lessons — the AI drafts the full text from a title, topic and technical field, and describes the images each passage would call for.
  • Image generation — each description becomes a real image, generated and stored by the system, with a configurable image model.

In all of them the AI proposes and a person decides: the proofreader accepts or rejects the correction, the teacher checks the feedback before it counts. That is not an interface detail — it is what makes the tool usable inside an educational institution.

How this is built

Wiring a model to an API is the easy part. What keeps the feature alive in production is everything around it:

API
OpenAI Responses API, chaining the conversation by previous response id
Reliable output
structured output with JSON Schema — the system receives data, not prose to parse
Live response
streaming over Server-Sent Events
Cost
per-user hourly limit, token ceiling computed from what was requested
Observability
every call recorded in a table: who asked, for what, what it cost, whether it worked or which error it hit
Secrets
key in an environment variable, out of version control, with an example file carrying no real value

Prompt engineering in practice

The prompt that generates the questions does not say "write 10 questions". It carries the rules a good assessment item has to follow, and each of them is there because its absence showed up in the output:

  • short stems, because they will be read off a projector, from a distance;
  • plausible distractors, the same length and style as the correct option — an obvious distractor measures nothing;
  • no "all of the above";
  • the position of the correct option varying across questions;
  • and the rule that matters most in technical training: never invent a standard, a value or a figure.

AI-assisted development

I also use AI to write software, and I treat that as engineering rather than a shortcut. What makes the difference is not the model — it is the environment built around it.

  • Curated per-repository context — each project has an instruction document carrying the code conventions, the helpers that already exist (so they are not duplicated), and a section of known traps: the bugs that cost dearly once and must not come back. That is what stops the assistant from reintroducing an old problem.
  • Code graph — the repository is indexed and queryable through an MCP server, used to narrow the scope before reading: find the function, measure the blast radius of a change. With one explicit rule, because graphs are wrong sometimes: the source beats the graph.
  • Hook automation — the index updates itself on every file edit, so it is never stale at the moment a decision depends on it.
  • Spec-driven development — a large change does not start in the code: it starts as a specification, becomes a plan broken into tasks with a definition of done, and each task leaves a record of what was done and what was left open. When the process has to be adapted, the decision is written down together with the cost of being wrong about it.
  • Review as a separate pass — whoever wrote it does not approve it. Verification is its own step, with the diff in hand.

The practical result is being able to work safely in a large legacy system — PHP accumulated over years, files thousands of lines long, exporters with known traps — without having to remember all of it. This portfolio was built the same way, from the specification to the contrast check.
